What it is

PaymentGuard AI is a payment-authorization workflow built with the IRIS 2026.3 AI Hub Early Access build — an entry for the InterSystems Programming Contest AI Agent in Interoperability Workflows. Every inbound payment flows through an interoperability production where a hybrid decision strategy applies:

  • Deterministic rules first — sanctions, blacklists, hard limits and velocity spikes are blocked instantly, and fully-trusted payments are approved instantly, with zero LLM cost.
  • The gray zone goes to an AI Hub agent — a real %AI.Agent ("AI Risk Agent") with read-only SQL tools over the payment platform's own data. It grounds its APPROVE / REVIEW / BLOCK decision in live customer history, velocity, device reputation and merchant statistics.
  • Fail-safe by design — if the agent errors, times out or returns malformed output, the payment degrades to a human-review queue, never to a silent approve and never to a blind block.

Every decision — rules, agent, mock or fallback — lands in an immutable audit record with full cost observability: prompt/completion tokens, tool-call count, latency, model and the persisted AI Hub session id (replayable via %AI.Agent.Session).

The architecture

REST callers enter through the PaymentGuard REST business service; the Decision business process orchestrates enrichment (live SQL), the deterministic rule engine, and — only for the gray zone — the AI Hub agent, then routes the outcome to settlement, a human review queue or a fraud alert. Every hop is a traced interoperability message in the Management Portal message viewer.

The system in one picture: the Web Gateway sidecar fronts the NoPWS AI EAP container, and inside it a single interoperability production — REST BS → Decision BP → Settle / Review / Alert operations, with the AI Risk Agent consulted synchronously for gray-zone payments and every transaction persisted with its 256-dimension similarity vector. The interactive version (docs/architecture.en.html in the repository) adds pan/zoom, relationship tracing and per-node source links.

A real gray-zone decision from the demo run: the agent queries live IRIS data through its SQL tools, then answers in strict JSON — action, risk score, grounded reasons, tokens and latency.

The production item "PaymentGuard AI Risk Agent" is the centerpiece: an ordinary Ens.BusinessOperation that hosts the AI Hub agent in-process. A business process talks to the AI exactly like it talks to any other operation — queued, traced, retryable — while the operation internally runs %AI.Agent, persists the session and reports token usage back into the message flow.

The agent

PaymentGuard.Agent.RiskAgent extends %AI.Agent:

  • INSTRUCTIONS — a payment-underwriter persona with an explicit decision policy (BLOCK only on converging signals, REVIEW when unusual-but-plausible, APPROVE when consistent with established profile) and a strict JSON output contract: action, risk_score, confidence, snake_case reasons[], a human-readable summary.
  • Tools — six read-only tools (%AI.Tool methods): customer profile, recent transactions, payment velocity, device reputation, merchant statistics, semantic similarity search. Each is live SQL over the production's own tables; the agent decides what to verify.
  • Provider-agnostic — DeepSeek out of the box (AI_PROVIDER / AI_MODEL / <PROVIDER>_API_KEY in .env); any AI Hub provider works.

The decision process treats the agent like any fallible dependency: its answer is parsed defensively (plain JSON, fenced JSON, JSON-in-prose), validated against the contract, and any failure degrades to a human REVIEW with a reason code — an AI outage never silently approves and never blocks revenue.

Replaying what actually happened

An agent that moves money has to be auditable, not just fast. PaymentGuard keeps three layers of evidence for every decision, all inside the box:

  • Every hop — Ens.MessageHeader records each message as it travels REST → decision process → agent → settlement / review / alert, with timestamps and body references.
  • Every reasoning step — the operation persists the %AI.Agent.Session: the context the agent saw, each tool call, each result, the final answer.
  • Every cost — the immutable decision record stores prompt/completion tokens, tool calls, latency, model and the session id.

The dashboard's Flow panel turns those layers into a replay. Trigger any action and its task enters a queue; when the decision lands, the real trace (GET /api/trace) replays hop by hop over the production topology with the real millisecond timings. Because it is all standard interoperability machinery, the same session deep-links into the Management Portal's Message Viewer (?SESSIONID=…) — the dashboard is a convenience layer over tooling that ships with the product:

Two notes from running this in production. Latency: after slimming the context the agent ships (~2.5k prompt tokens; top-3 history and top-3 vector neighbors instead of five), gray-zone decisions land in 1.4–1.9 s end to end while rules stay in single-digit milliseconds at zero tokens. Failure mode: the agent call is capped at 20 s — a hung LLM degrades to a human-review queue item instead of wedging the pipeline. An AI outage never blocks revenue, and never approves silently.

Healthcare claims: the same engine, one more fraud domain

Health-insurance claim settlement is just a payment with extra vocabulary: the member is the customer, the provider is the merchant, and the claim carries procedure, diagnosis and city. Those fields ride the entire pipeline unchanged — rules, enrichment, agent context, audit trail — so the production learns a second fraud domain through a purely additive change. Two deterministic claim rules extend the rule engine: the same member settling the same procedure in another city within 7 days of a settled claim blocks instantly (DUPLICATE_CROSS_CITY_CLAIM), and providers reuse the merchant blacklist (BLACKLISTED_MERCHANT). The agent's instructions map the claim vocabulary and the duplicate-reimbursement pattern, so gray-zone claims get correlated against the member's settlement history.

The demo scenario: member memb_001 settled a full-price cataract surgery (CNY 12,800) at Shanghai Renji Hospital 3 days ago. Three claims via POST /api/claims, three mechanisms.

The same surgery filed in Beijing — the rule engine answers in milliseconds, zero tokens:

curl -s -X POST localhost:8082/paymentguard/api/claims -H "Content-Type: application/json"   -d '{"member_id":"memb_001","provider":"Beijing Union Medical College Hospital","procedure":"CATARACT_SURGERY","diagnosis":"H25.9","amount":12800,"city":"Beijing","currency":"CNY"}'

BLOCK · RULES — DUPLICATE_CROSS_CITY_CLAIM — "Insured member settled procedure CATARACT_SURGERY in Shanghai within the last 7 days (prior claim claimhist_memb_001_CATARACT_SURGERY_3 on 2026-10-25) - duplicate cross-city reimbursement"

The same surgery back in Shanghai — same city, so the rule doesn't fire. The gray zone goes to the agent, which correlates the settled surgery with today's blocked Beijing attempt:

BLOCK · AGENT (deepseek-chat), risk 92, confidence 0.9 — reasons duplicate_reimbursement, same_procedure_multiple_cities, same_procedure_settled_3_days_ago, prior_attempt_blocked_today, amount_matches_duplicate_exactly — "Member Zhang Wei already has CATARACT_SURGERY (H25.9) settled at Shanghai Renji Hospital on 2026-10-25 for CNY 12,800; a further identical claim was attempted at Beijing Union Medical College Hospital today and blocked, and now the same procedure/amount is presented again in Shanghai. This is a duplicate reimbursement attempt across providers/cities and should be declined and escalated." — 1,985 prompt + 154 completion tokens, 1.8 s.

And a claim from a blacklisted provider never reaches the LLM: BLACKLISTED_MERCHANT, instant block, zero tokens. The seed data ships four members, four hospitals and dialysis / surgery / imaging history, and the %UnitTest suite grew to 24 — claim endpoint mapping, the cross-city duplicate rule, the provider blacklist, and the agent-correlated claim flow.

Similar transactions: IRIS Vector Search via Embedded Python

The newest sense in the decision path is memory — this payment resembles something we have seen before. Two Embedded Python components deliver it, both [Language = python] methods written against the standard library only — no pip packages, no external API:

  • A logistic risk prior — PaymentGuard.Rules.PyModel scores the enrichment context offline (amount vs baseline, velocity, device sharing, geo mismatch, KYC) and rides into the agent's context as ml_model: one advisory signal, never an oracle — if Python is unavailable the flow simply continues without it.
  • Vector-similar transactions — PaymentGuard.Vector.Embedder hashes the structured transaction features (procedure, diagnosis, provider, city, channel, currency, amount band) into a 256-dimension L2-normalized embedding. Deterministic and offline: identical inputs always produce the identical vector, so a query embedding can be recomputed from a row's features without ever reading a stored vector back.

Every transaction the production persists carries a VECTOR(double, 256) embedding column, and a VECTOR_COSINE top-K search feeds two paths: a pre-computed similar_transactions section in every gray-zone risk context, and a sixth agent tool — SearchSimilarTransactions — so the underwriter can pull semantic neighbors on demand, mid-reasoning. Humans get the same view at GET /api/similar?txn_id=…:

curl -s "localhost:8082/paymentguard/api/similar?txn_id=claimhist_memb_001_CATARACT_SURGERY_3&limit=3"

 {"txn_id":"…MRI_BRAIN claim…","procedure":"MRI_BRAIN","city":"Shanghai","similarity":0.307}]}

The NoPWS surprise (or: how to serve anything from these builds)

The 2026.3 AI Hub EAP builds are NoPWS — the private web server on port 52773 is disabled entirely; no portal, no REST, nothing HTTP from the IRIS container. PaymentGuard therefore ships a standard InterSystems Web Gateway sidecar and documents the three things that made it work:

  • Credentials live in CSP.ini — this gateway build ignores the usual ISC_CSP_IRIS_* env vars; the [LOCAL] section needs Username=CSPSystem / Password=SYS, and the EAP builds no longer create the CSPSystem user, so the installer creates it and enables %Service_WebGateway.
  • The Apache module dispatches by file extension (CSPFileTypes csp cls zen cxw) — extensionless REST URLs never reach IRIS. The stack internally rewrites them to a .csp twin route (mod_rewrite + a doubled UrlMap), so pretty URLs like POST /payments work unchanged.
  • Unauthenticated demo access needs the web apps' roles granted to UnknownUser, or every request dies with a <PROTECT>/403 before reaching your dispatch class.

The dashboard itself is plain static HTML served straight from Apache (mounted web/ directory), polling the API — no build step, no npm.

Deployment and distribution

The whole stack is containerized — docker compose up -d --build starts IRIS (the AI Hub EAP community image) plus the Web Gateway sidecar described above. Source and one-command quick start: github.com/Dylan5237/payment-guard-ai.

An online demo is live at 43.139.159.100:8082/paymentguard — the dashboard, the REST API at /paymentguard/api and the production behind it, deciding in live DeepSeek mode (Management Portal: /csp/sys/UtilHome.csp, SuperUser / SYS).

It also ships as an IPM package (module paymentguard): classes, REST web apps and the dashboard install with zpm "install paymentguard" — and it is on Open Exchange as PaymentGuard AI.

No API key? The stack runs end-to-end in mock mode — a deterministic engine answers in the same JSON contract, so the flow, dashboard, audit trail and the whole %UnitTest suite work offline (30 tests, green).
